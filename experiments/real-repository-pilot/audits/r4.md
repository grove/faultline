Found two clear test gaps and one suspected authentication-precedence bug.

1. **Cross-host HTTPS upgrades lack protection**

   **What could go wrong:** A redirect from `http://example.com/a` to `https://another.example.com/b` must strip credentials. Moving the HTTPS-upgrade exception before the hostname check in [should_strip_auth](/SNAPSHOTS/r4/src/requests/sessions.py:154) could leak them.

   **Why these tests may miss it:** The [host-change test](/SNAPSHOTS/r4/tests/test_requests.py:1940) keeps HTTP unchanged; the upgrade tests keep the hostname unchanged. Neither combines these conditions. The [docs](/SNAPSHOTS/r4/docs/user/quickstart.rst:226) explicitly require removing authorization off-host.

   **Smallest useful test:** Prepare an authenticated HTTP request, copy it with an HTTPS URL on another hostname, and call `rebuild_auth` with `trust_env=False`. Assert that the redirected copy lacks `Authorization` and the original retains it.

   **Confidence and uncertainty:** High-confidence **missing test protection**. The current hostname check handles this correctly; no implementation bug is alleged.

2. **The port-change test also changes scheme**

   **What could go wrong:** Credentials could survive `https://example.com:8443/a` → `https://example.com:9443/b` if the [final decision](/SNAPSHOTS/r4/src/requests/sessions.py:173) stopped considering port changes.

   **Why these tests may miss it:** [test_should_strip_auth_port_change](/SNAPSHOTS/r4/tests/test_requests.py:1969) changes both HTTP→HTTPS and 1234→4321. Scheme comparison alone satisfies its assertion. The default-port tests protect equivalent port spellings, but provide no stripping case where only the port changes.

   **Smallest useful test:** Add a parameterized case for HTTP and HTTPS with hostname and scheme fixed and distinct nondefault ports. Assert `should_strip_auth` returns true. Exercise one through `rebuild_auth` with `trust_env=False` and assert the copied request loses its authorization.

   **Confidence and uncertainty:** High-confidence **missing test protection**, supported by the current port comparison. Existing tests already protect retaining authorization across explicit/implicit default-port equivalents.

3. **Same-origin redirects can replace explicit credentials with `.netrc` credentials**

   **What could go wrong:** Prepare `https://example.com/start` with explicit account A while `.netrc` supplies account B. On a redirect to `/finish`, stripping is unnecessary, but [rebuild_auth](/SNAPSHOTS/r4/src/requests/sessions.py:329) unconditionally reapplies available `.netrc` credentials. Source inspection indicates the redirected request switches accounts.

   **Why these tests may miss it:** The [precedence test](/SNAPSHOTS/r4/tests/test_requests.py:683) tests requests without redirects. The [retention test](/SNAPSHOTS/r4/tests/test_requests.py:1933) supplies no controlled competing `.netrc` identity. The [autouse fixture](/SNAPSHOTS/r4/tests/conftest.py:25) clears proxy variables only.

   **Smallest useful test:** Mock `requests.sessions.get_netrc_auth` to return B. Prepare a request with explicit A through `Session.prepare_request`, then rebuild authentication on a copy whose URL changes only its path. Assert the authorization remains A.

   **Confidence and uncertainty:** **Suspected implementation bug**, with medium confidence in the redirect contract. The [documented precedence](/SNAPSHOTS/r4/docs/user/quickstart.rst:221) and [initial preparation](/SNAPSHOTS/r4/src/requests/sessions.py:535) favor explicit authentication. An intentional, documented redirect-specific exception would refute that expectation.
